## 3. Data model

### 3.1 Principles

- **Movies are shared.** One row per real movie, identified by normalized title + release year.
- **Fact content belongs to a movie** (`MovieFact`). It contains no personal data and can be shared across users.
- **Fact history belongs to a user** (`FactDelivery`): who was shown which fact, and when.
- **The database clock is the single source of time.** All timestamps are `timestamptz`. All freshness comparisons use Postgres `now()` in SQL, never the app server's or the client's clock.
- **ACID:**
  - Multi-row writes happen in one transaction.
  - Constraints and foreign keys enforce consistency in the database, not only in app code.
  - Lease acquisition is a single atomic statement, so the default isolation level (Read Committed) is sufficient.
- **No fact deletion.** Growth is bounded by the 60-second window, and indexes keep the "latest" lookups fast.
- **Extensible:**
  - One favorite per user today, enforced by a temporary unique constraint. Dropping that constraint allows multiple favorites with no data migration.
  - `Movie` can later gain an external id (e.g., TMDB).

### 3.2 Auth tables

`User`, `Session`, `Account`, `Verification` are **generated by the Better Auth CLI**. Do not hand-write them; check current Better Auth docs for the exact command and output. The one change to the CLI output is adding `@db.Timestamptz(3)` to every `DateTime` field, so all timestamps in the database are `timestamptz`. Beyond that, we add only relation fields to `User`:

```prisma
// added to the generated User model
favorites  UserFavoriteMovie[]
deliveries FactDelivery[]
leases     FactGenerationLease[]
```

Better Auth requires `User.name`. Configure the Google provider's profile mapping so a missing name falls back to the part of the email before the `@`. `image` stays nullable; the UI shows an initials avatar when it is missing.

### 3.3 Application tables

```prisma
model Movie {
  id              String    @id @default(cuid())
  title           String                       // display form, as first entered (trimmed, whitespace collapsed)
  normalizedTitle String                       // see §4.1
  releaseYear     Int
  status          MovieStatus @default(PENDING)
  statusUpdatedAt DateTime?   @db.Timestamptz(3)
  createdAt       DateTime    @default(now()) @db.Timestamptz(3)

  favorites UserFavoriteMovie[]
  facts     MovieFact[]
  leases    FactGenerationLease[]

  @@unique([normalizedTitle, releaseYear])
}

enum MovieStatus {
  PENDING        // saved, not yet checked by the model
  VERIFIED       // the model recognized it and produced a fact
  NOT_RECOGNIZED // the model did not recognize this title + year
}

model UserFavoriteMovie {
  userId    String
  movieId   String
  createdAt DateTime @default(now()) @db.Timestamptz(3)

  user  User  @relation(fields: [userId], references: [id], onDelete: Cascade)
  movie Movie @relation(fields: [movieId], references: [id], onDelete: Restrict)

  @@id([userId, movieId])
  @@unique([userId]) // TEMPORARY: one favorite per user. Drop to allow many.
}

model MovieFact {
  id        String   @id @default(cuid())
  movieId   String
  content   String
  model     String   // OpenAI model that produced it
  createdAt DateTime @default(now()) @db.Timestamptz(3)

  movie      Movie          @relation(fields: [movieId], references: [id], onDelete: Restrict)
  deliveries FactDelivery[]

  @@unique([id, movieId]) // target of FactDelivery's composite foreign key
  @@index([movieId, createdAt(sort: Desc)])
}

model FactDelivery {
  id          String   @id @default(cuid())
  userId      String
  movieId     String   // denormalized for a single-index "latest for user + movie" lookup
  movieFactId String
  deliveredAt DateTime @default(now()) @db.Timestamptz(3)

  user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  movieFact MovieFact @relation(fields: [movieFactId, movieId], references: [id, movieId], onDelete: Restrict)

  @@index([userId, movieId, deliveredAt(sort: Desc)]) // latest fact for user + movie
  @@index([movieFactId, userId])                      // has this user seen this fact?
}

model FactGenerationLease {
  userId      String
  movieId     String
  holderId    String   // random id of the request holding the lease
  lockedUntil DateTime @db.Timestamptz(3)

  user  User  @relation(fields: [userId], references: [id], onDelete: Cascade)
  movie Movie @relation(fields: [movieId], references: [id], onDelete: Cascade)

  @@id([userId, movieId])
}
```

Notes:

- **Composite foreign key.** `FactDelivery.movieId` duplicates `MovieFact.movieId` for query speed. The composite foreign key `(movieFactId, movieId) → MovieFact(id, movieId)` makes the database guarantee they always match.
- **Timestamps.** Confirm in the generated migration SQL that `@default(now())` becomes a database default and that Prisma Client does not send app-server timestamps on insert. If it does, switch to `@default(dbgenerated("now()"))`.
  - **Verified (Prisma 7.10):** with `@default(now())`, Prisma Client *does* send the app server's time on insert. All application-table timestamps (`createdAt`, `deliveredAt`) therefore use `@default(dbgenerated("transaction_timestamp()"))`. That's the same value as `now()`, but avoids `dbgenerated("now()")`, which Prisma reads back as `@default(now())` and re-emits in every migration (schema drift). A test checks the actual INSERT SQL.
- **Relation fields** (`favorites`, `facts`, etc.) are Prisma navigation fields, not database columns.
- **`Movie.status`** is set only by the fact flow (§7.2 step 7), never at onboarding. Status changes are monotonic toward `VERIFIED`:
  - A valid `found: true` result may move `PENDING` or `NOT_RECOGNIZED` to `VERIFIED`. A real fact is stronger evidence than a "not recognized".
  - A `found: false` result may move only `PENDING` to `NOT_RECOGNIZED`.
  - `VERIFIED` is never downgraded.
  - Every status change also sets `statusUpdatedAt = now()`.

  Enforce this with conditional updates (`UPDATE … WHERE status IN (…)`), so concurrent requests from different users can't flip it back and forth.

## 4. Validation and normalization

### 4.1 Title normalization (`normalizedTitle`)

Applied server-side:

1. Unicode NFKD.
2. Strip combining marks (accents): "Amélie" → "amelie".
3. Lowercase.
4. Replace every character that is not a letter or number (Unicode `\p{L}` / `\p{N}`) with a space.
5. Collapse whitespace and trim.

Example: "Dune: Part Two" → "dune part two". Non-Latin titles keep their letters.

The display `title` is only trimmed with whitespace collapsed. When a movie already exists, the first-entered display title is kept.

### 4.2 Input rules (Zod, server-side)

- **`title`:**
  - String, trimmed.
  - 1–100 characters.
  - No control characters.
  - Must be non-empty after normalization.
- **`releaseYear`:** integer, 1888 ≤ year ≤ (current year + 2). Required.
- **Search `q`:** 1–100 characters raw, and at least 2 characters after normalization.
- **Delete confirmation:** body must be exactly `{ "confirm": "delete" }`.

Validation failures return `422 VALIDATION_ERROR` with field-level details. The 400 for a wrong delete confirmation is the one exception (see §6).

## 5. Auth and routing

- **`/`:**
  - Unauthenticated: landing page with "Sign in with Google".
  - Authenticated: redirect based on onboarding state.
- **After Google sign-in:**
  - No favorite → `/onboarding`.
  - Has a favorite → `/dashboard`.
- **`/onboarding`:**
  - Requires a session.
  - Redirects to `/dashboard` if a favorite already exists.
- **`/dashboard`:**
  - Requires a session; otherwise redirect to `/`.
  - Redirects to `/onboarding` if there is no favorite.

**Two layers of checks (defense in depth):**

1. **Edge layer** (`middleware.ts`, or `proxy.ts` on Next.js 16+; check the installed version): an *optimistic* check only, based on session-cookie presence, for fast redirects. It is never the security boundary (see CVE-2025-29927).
2. **Data access layer:** `lib/server/session.ts` exports `requireUser()`. Every page, route handler, and service entry point that touches user data calls it or receives a user from it. This is the authoritative check against the session in the database.

**Sessions:**

- Database sessions, revocable server-side.
- Cookies are HttpOnly, Secure (in production), and SameSite=Lax.
- CSRF and OAuth state / PKCE are handled by Better Auth.

## 6. API contract

Better Auth owns `/api/auth/*`. Every endpoint below:

- Requires a session (`401 UNAUTHENTICATED` otherwise).
- Takes the user's identity only from the session. No endpoint accepts a user id.
- Returns JSON.

**Error shape (all errors):**

```json
{ "error": { "code": "MOVIE_NOT_RECOGNIZED", "message": "We couldn't find any facts about that movie." } }
```

Validation errors may add `"details": { "fieldErrors": { ... } }`. Messages are safe for end users. Internal errors and OpenAI error details are never returned, only logged server-side.

### `GET /api/me`

`200`:

```json
{
  "user": { "id": "…", "name": "…", "email": "…", "image": "… | null" },
  "favoriteMovies": [{ "id": "…", "title": "Dune", "releaseYear": 2021, "status": "VERIFIED" }]
}
```

### `GET /api/movies/search?q=du`

`200 { "movies": [{ "id", "title", "releaseYear" }] }`

- At most 8 results.
- **`VERIFIED` movies only.**
- Titles that start with the query come first, then titles that contain it; ties are ordered alphabetically.
- `422` on an invalid `q`.

### `POST /api/me/favorite-movies`

Body: `{ "title": string, "releaseYear": number }`

| Status | Code | When |
|---|---|---|
| 201 | — | Favorite created → `{ "movie": { id, title, releaseYear, status } }` |
| 200 | — | The same movie is already the user's favorite (idempotent retry) |
| 409 | `FAVORITE_EXISTS` | The user already has a *different* favorite |
| 422 | `VALIDATION_ERROR` | Invalid input |

Flow: see §9.

### `GET /api/movies/:movieId/fact`

`200`:

```json
{
  "fact": { "id": "…", "content": "…", "createdAt": "…" },
  "source": "cache | generated | pool | fallback",
  "stale": false
}
```

- **`source`:**
  - `cache`: the user's own delivery from the last 60 seconds.
  - `generated`: newly created by OpenAI for this request.
  - `pool`: an existing fact delivered from the shared pool (pool strategy only).
  - `fallback`: an older fact served because generation failed or is in progress elsewhere.
- **`stale`:** `true` exactly when `source = fallback`.

| Status | Code | When |
|---|---|---|
| 404 | `NOT_FOUND` | The movie is not one of this user's favorites. Use 404, not 403, so other users' data isn't revealed. |
| 422 | `MOVIE_NOT_RECOGNIZED` | The movie's status is `NOT_RECOGNIZED` (already known, or just learned from the model). The user keeps this favorite; there is no prompt to change it. |
| 503 | `FACT_UNAVAILABLE` | Generation failed and no fallback fact exists; or generation is in progress and nothing exists yet. The message should invite the user to retry. |

### `DELETE /api/me`

Body: `{ "confirm": "delete" }`

| Status | Code | When |
|---|---|---|
| 204 | — | User and all personal data deleted; all sessions gone |
| 400 | `BAD_CONFIRMATION` | Confirmation missing or wrong |

No `PUT` or `PATCH` endpoints exist: editing a favorite is out of scope.

## 7. Fact generation (`GET /api/movies/:movieId/fact`)

### 7.1 Constants and configuration

| Name | Value |
|---|---|
| Cache window | 60 seconds (DB time) |
| Lease TTL | 20 seconds |
| Generation deadline | 12 seconds total for OpenAI + retry + moderation (a single `AbortSignal`) |
| Lost-lease polling | Every ~250 ms, for up to 2 seconds |
| `FACT_STRATEGY` | `generate` (default) or `pool` |
| `FACT_POOL_SIZE` | `10` |

The lease TTL must always exceed the generation deadline, so a lease can't expire while its holder is still working.

### 7.2 Algorithm

1. **Authorize.**
   - Call `requireUser()`.
   - Confirm `movieId` is in the user's `UserFavoriteMovie`; otherwise return `404 NOT_FOUND`.
   - If the movie's status is `NOT_RECOGNIZED`, return `422 MOVIE_NOT_RECOGNIZED` immediately. **No API call**, so repeated refreshes on a junk title cost nothing.
2. **Cache check.** If the user's latest `FactDelivery` for this movie has `deliveredAt > now() - interval '60 seconds'`, return it as `source: cache`.
3. **Acquire the lease** with one atomic statement:

   ```sql
   INSERT INTO "FactGenerationLease" ("userId", "movieId", "holderId", "lockedUntil")
   VALUES ($userId, $movieId, $holderId, now() + interval '20 seconds')
   ON CONFLICT ("userId", "movieId") DO UPDATE
     SET "holderId" = EXCLUDED."holderId", "lockedUntil" = EXCLUDED."lockedUntil"
     WHERE "FactGenerationLease"."lockedUntil" < now()
   RETURNING "holderId";
   ```

   A returned row whose `holderId` is ours means we won. No row means another request holds the lease. Use the actual table and column names from the generated migration. Run it via `$queryRaw` tagged templates only.
4. **Lost the lease.** Poll the cache check (step 2) every ~250 ms for up to 2 s.
   - If a fresh delivery appears, return it as `cache`.
   - Otherwise use the fallback order (§7.4).
   - If there is no fallback, return `503 FACT_UNAVAILABLE`.
5. **Won the lease.** Re-run the cache check before doing anything. Another request may have finished between steps 2 and 3. If a fresh delivery exists now, release the lease and return it as `cache`.
6. **Choose a fact source:**
   - **`generate`:** call OpenAI (§8).
   - **`pool`** (`VERIFIED` movies only; a `PENDING` movie always generates):
     1. If a `MovieFact` exists for this movie with no `FactDelivery` for this user, deliver the oldest one (`source: pool`). No API call.
     2. Otherwise, if the movie has fewer than `FACT_POOL_SIZE` facts, call OpenAI.
     3. Otherwise (the user has seen all of them), deliver the fact this user saw longest ago (`source: pool`).
7. **Handle the OpenAI result:**
   - **`found: true`, valid, and not flagged by moderation.** In one transaction:
     - Insert the `MovieFact`.
     - Insert the `FactDelivery`.
     - Set `Movie.status = VERIFIED` (conditional update, see §3.3 notes).

     Return it as `generated`.
   - **`found: false`:**
     - If the movie is `PENDING`, set it to `NOT_RECOGNIZED` (conditional update) and return `422 MOVIE_NOT_RECOGNIZED`.
       - If that conditional update changes 0 rows (a concurrent request already changed the status), re-read the status. If it is `VERIFIED`, treat this as a generation failure and use the fallback order. If it is `NOT_RECOGNIZED`, return `422 MOVIE_NOT_RECOGNIZED`.
     - If the movie is already `VERIFIED`, treat it as a generation failure (the model is being inconsistent) and use the fallback order.
   - **Failure** (timeout, API error, invalid output, moderation flag): use the fallback order (§7.4).
8. **Always release the lease** in a `finally` block:

   ```sql
   DELETE FROM "FactGenerationLease" WHERE "userId" = $1 AND "movieId" = $2 AND "holderId" = $holderId
   ```

   Only the holder can release its own lease. If the release never happens (e.g., a crash), the TTL frees the lease. Correctness does not depend on the release, because step 5 re-checks.

### 7.3 Delivering an existing fact (pool)

Insert a `FactDelivery` for the chosen `MovieFact`. That delivery becomes the user's cached fact for the next 60 seconds.

### 7.4 Fallback order

1. The user's own most recent delivery for this movie.
2. The most recent `MovieFact` for this movie from any user. Only for a `VERIFIED` movie.
3. Nothing is available: `503 FACT_UNAVAILABLE`.

Serving a fallback does **not** insert a `FactDelivery`.

### 7.5 Concurrency edge case: deletion mid-generation

If the user is deleted while their generation is in flight, the delivery insert fails with a foreign-key error (Prisma `P2003`). Catch exactly that error, log it, and discard the result. The transaction rolls back cleanly.

## 8. OpenAI integration

- **Location.** All OpenAI code lives in `lib/server/openai/`, which starts with `import "server-only"`. The prompt text is never sent to the client, and responses contain only the fact text.
- **Assume the prompt can leak.** It contains no secrets. Security comes from the layers below, not from hiding the prompt.
- **Inputs to the model:** the movie's display title and release year only. **No personal data is ever sent.** The user's name is added at display time on our side.
- **Model:** set by `OPENAI_MODEL`, defaulting to a current small, inexpensive model (choose it at build time from the current OpenAI docs).
- **Call settings:**
  - Overall deadline of 12 s via `AbortSignal`.
  - At most 1 retry, only for connection errors, 429, or 5xx.
  - Output capped at ~150 tokens.
- **Structured output:** a JSON schema enforcing `{ "found": boolean, "fact": string | null }`.
  - Parse it with Zod.
  - Reject if `found` is true and `fact` is empty or longer than 500 characters.
  - Any parse or validation failure counts as a generation failure.
- **Prompt-injection defenses (layered):**
  1. Input limits from §4.2: 100 characters, single line, no control characters.
  2. Instructions go in the system message. The title and year go in the user message, inside clear delimiters, with an explicit rule that they are data identifying a film and never instructions.
  3. Instruct the model to return `found: false` when it doesn't recognize a film with that title from that year, rather than inventing a fact.
  4. Structured output plus validation.
  5. Least privilege: no tools, no data access, no secrets in context.
  6. Moderation: run the generated fact through OpenAI's moderation endpoint (use the current moderation model from the docs) before storing it. A flagged fact counts as a generation failure. This matters most in `pool` mode, where facts are shown to other users.
  7. Safe rendering: React text only, never `dangerouslySetInnerHTML`.
- **Dependency injection.** Define a `FactGenerator` interface (`generate({ title, releaseYear, signal }) → { found, fact, model }`). The production implementation wraps OpenAI; tests inject a fake.

## 9. Onboarding flow (`POST /api/me/favorite-movies`)

1. `requireUser()`; validate the body (§4.2); compute `normalizedTitle`.
2. **Existing favorite:**
   - Same `(normalizedTitle, releaseYear)` → `200` with that movie (idempotent).
   - Different movie → `409 FAVORITE_EXISTS`.
3. **Find or create the movie** by `(normalizedTitle, releaseYear)`, race-safely (`INSERT … ON CONFLICT DO NOTHING`, then select). A new movie starts as `PENDING`. An existing movie keeps its status, whatever it is.
4. **Create the `UserFavoriteMovie`** in the same transaction → `201`.
5. **No OpenAI call and no verification at onboarding.** Onboarding is fast and works even when OpenAI is down. Whether the movie is recognized is learned later, from the first fact request (§7.2 step 7).
6. **Concurrent double-submit:** the unique constraints guarantee at most one favorite; the losing insert maps to the idempotent `200` or the `409`.

Even if the movie is already `NOT_RECOGNIZED` (another user entered it earlier), onboarding links it normally. The dashboard then shows the not-recognized message. Users are never asked to change their favorite.

## 10. Autocomplete (onboarding form)

- **When requests fire:** calls `GET /api/movies/search` after at least 2 typed characters, debounced ~250 ms.
- **Suggestions:** `VERIFIED` movies only, at most 8. `PENDING` and `NOT_RECOGNIZED` titles are never suggested. Selecting one fills both title and year.
- **Free entry:** the user can always ignore the suggestions and type any title and year.
- **One submit path:** the form always submits `{ title, releaseYear }`; the server resolves it (§9). There is no separate "submit by movie id" path.
- **Accessibility:** the accessible combobox pattern (`role="combobox"`, listbox, `aria-activedescendant`), with arrow keys, Enter, and Escape.
- **Query safety:** use Prisma `startsWith` / `contains` (parameterized) on `normalizedTitle`. Normalization already strips `%` and `_`; confirm Prisma's wildcard handling regardless.
- **Not handled now:** offensive or spammy titles (see §17).

- **Server-rendered immediately:**
  - The user's name (or the email-prefix fallback) and email.
  - Photo, or an initials avatar.
  - Favorite movie as "Title (Year)".
  - Logout button.
- **Greeting:** "Hey {first name}, here's a fact about *Title*", composed on our side.

  - Loading.
  - Success.

## 12. Account deletion (`DELETE /api/me`)

1. `requireUser()`; validate the confirmation body.
2. **Best-effort Google token revocation.** Read the Google token from the user's `Account` row and POST it to Google's OAuth revoke endpoint (check Google's current docs). A failure is logged and **never blocks deletion**.
   - Limitation: if the stored access token has expired, Google may reject the call. Reliable revocation would require storing a refresh token, which we deliberately don't do.
3. **Hard delete** the `User` in a transaction.
   - **Cascades remove:** sessions, accounts, favorites, deliveries, and leases.
   - **Kept:** `Movie` and `MovieFact`, which are shared and contain no personal data.
4. **Response:** `204`. The sessions are gone, so the user is logged out everywhere.
5. **Signing in again** later creates a fresh user, who goes through onboarding.

Implement this in our own endpoint so the API contract stays ours. Use Better Auth's built-in delete-user APIs only if they fit this flow; check current docs.

## 14. Testing

Vitest, against a real Postgres test database (`TEST_DATABASE_URL`, a separate `movie_memory_test` database on the local Postgres server).

- **Setup:**
  - Apply migrations to the test database.
  - Truncate tables between tests.
  - Inject a fake `FactGenerator`.
  - Mock the session lookup at `requireUser()`.
- **Time:** tests control it by inserting rows with backdated timestamps in SQL (e.g., `now() - interval '61 seconds'`). There is no fake clock.

Required coverage:

1. **Cache window:**
   - A delivery 59 s old → `cache`, with no generator call.
   - 61 s old → `generated`, with one generator call.
2. **Authorization:**
   - Every endpoint returns 401 without a session.
   - Fetching a fact for a movie that isn't the user's favorite → 404.
   - User B cannot get user A's facts.
3. **Concurrency:** 5 parallel fact requests after the window expires → exactly **1** generator call; every response gets the same fact or a valid fallback.
4. **Failure handling:**
   - The generator throws or times out → the user's last fact (`fallback`, `stale: true`).
   - With no user fact, another user's fact for the same movie.
   - With no fact at all → 503.
5. **Lease:**
   - An expired lease can be taken over.
   - A holder only releases its own lease.
6. **Pool strategy:**
   - Unseen facts are served first.
   - The `FACT_POOL_SIZE` cap is respected.
   - Once everything is seen, the least-recently-seen fact is served.
7. **Onboarding:**
   - Onboarding never calls the generator; a new movie is saved as `PENDING`.
   - An existing movie keeps its status.
   - A same-movie retry → 200; a different movie → 409.
8. **Movie status:**
   - `PENDING` + `found: false` → `NOT_RECOGNIZED` and 422.
   - `PENDING` + `found: true` → `VERIFIED`.
   - `NOT_RECOGNIZED` → 422 with **no** generator call.
   - `VERIFIED` + `found: false` → treated as a failure (fallback), with the status unchanged.
   - `PENDING` + `found: false` racing a concurrent `VERIFIED` (the conditional update changes 0 rows) → fallback, with the status staying `VERIFIED`.
9. **Normalization and validation:** unit tests for §4.
10. **Deletion:**
   - Personal data is removed and shared facts survive.
   - A bad confirmation → 400.
   - A revocation failure doesn't block deletion.

## 15. Configuration

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Postgres connection (hosted Postgres in production usually requires SSL) |
| `TEST_DATABASE_URL` | Test database (local / CI only) |
| `BETTER_AUTH_SECRET` | Session signing secret (random, ≥32 bytes) |
| `BETTER_AUTH_URL` | Public base URL of the app (differs per environment) |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google OAuth credentials |
| `OPENAI_API_KEY` | OpenAI key (server-only) |
| `OPENAI_MODEL` | Model for fact generation |
| `FACT_STRATEGY` | `generate` (default) or `pool` |
| `FACT_POOL_SIZE` | Pool cap per movie (default 10) |

None of these use the `NEXT_PUBLIC_` prefix. Nothing secret reaches the browser. `.env.example` lists every variable, with no real values.

Google OAuth needs an authorized redirect URI for `http://localhost:3000`, plus one for the production domain if the app is deployed. Better Auth's docs give the exact callback path.

## 16. Deployment

The app is **not deployed** for the submission. It stays deployable on any Node host: no platform-specific code, all configuration through env vars, and migrations via `prisma migrate deploy` (never `migrate dev` outside local development).

The README contains:

1. **Running locally (primary path for reviewers):**
   - Install Postgres 18 (Homebrew) and create the `movie_memory` and `movie_memory_test` databases.
   - Create Google OAuth credentials with the localhost redirect URI.
   - Copy `.env.example` to `.env` and fill it in.
   - `npm install`, `npm run db:migrate`, `npm run dev`.
   - `npm run db:test:prepare`, `npm test`.
2. **Deploying (guide only):** a short, platform-neutral checklist plus notes for two common options:
   - **Checklist:**
     - A hosted Postgres with SSL.
     - Set all §15 env vars on the host.
     - Set `BETTER_AUTH_URL` to the production URL.
     - Add the production redirect URI in Google Cloud Console.
     - Run `prisma migrate deploy` once per deploy, before the new code serves traffic.
     - Build with `npm run build`, start with `npm start`.
   - **Vercel + Neon** (free tier):
     - Serverless, so there are many instances by default. The lease design (§7) already handles this.
     - Use Neon's pooled connection string for the app and the direct one for migrations.
     - Run migrations in the build step.
     - Configure OAuth for the production domain only (preview URLs change).
     - Confirm the function duration limit exceeds the 12 s generation deadline.
   - **Heroku** (paid):
     - Procfile with `web` (`npm start`) and `release` (`npx prisma migrate deploy`).
     - Heroku Postgres 18 (SSL), with config vars for env.
     - Heroku is in sustaining-engineering mode since February 2026 but remains usable.
3. **Production considerations already built in:**
   - Multi-instance-safe burst protection (the DB lease, not an in-memory lock).
   - The DB clock as the single source of time.
   - No transaction held during OpenAI calls, which is friendly to small connection limits.
