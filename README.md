# Movie Memory

Sign in with Google, tell us your favorite movie, and get a fun fact about it, generated by OpenAI and cached with correctness guarantees.

This is the take-home's **Base implementation + Variant A (backend: caching and correctness)**. It's built with Next.js (App Router), TypeScript, React, Tailwind CSS, Postgres, Prisma, Google OAuth (via Better Auth) and the OpenAI API.

## 1. What's implemented

**Base (required)**

| Requirement | Where |
|---|---|
| `/` unauthenticated → landing page with "Sign in with Google" | `src/app/page.tsx` |
| After login: first-time users → onboarding, returning users → dashboard | `src/lib/shared/routes.ts` (`decideRoute`) |
| Onboarding asks for the favorite movie; server-side validation (trim, 1–100 characters); stored in Postgres, linked to the user | `src/lib/shared/schemas.ts`, `src/lib/server/movies/favorites.ts` |
| Dashboard: name, email, photo (initials when missing), favorite movie, logout | `src/app/dashboard/page.tsx` |
| Logged out on `/dashboard` → redirected to login | `src/lib/server/page-guards.ts` |
| Fun fact from OpenAI, stored in the database | `src/lib/server/openai/`, `src/lib/server/facts/` |

**Variant A (chosen)**

| Requirement | How |
|---|---|
| 60-second cache window | The user's last delivery for this movie is reused if it's under 60 s old, **by the database clock**. Tested at 59 s vs 61 s. |
| Burst / idempotency protection | A database **generation lease** (the brief's "generation in progress" option, made atomic and expiring). 5 parallel requests → exactly 1 OpenAI call (tested). |
| Failure handling | OpenAI timeout/error → the user's most recent fact (marked stale), else another user's fact for the same movie, else a friendly "try again" error. |
| Backend tests | Cache window, authorization, and much more: 340+ tests against a real Postgres test database. |

**Security:** inputs are validated on the server with Zod; every query is scoped to the session user (another user's movie returns 404, not 403); no secrets reach the browser (no `NEXT_PUBLIC_` variables); a missing Google name falls back to the email prefix and a missing photo to initials.

**Additions beyond the brief** (kept small, each tested):
- An optional release year (it disambiguates remakes, e.g. *Dune* 1984 vs 2021).
- Autocomplete over known movies.
- Editing the favorite (`PUT /api/me/favorite-movie`).
- "Not recognized" detection for made-up titles.
- An opt-in shared fact pool (`FACT_STRATEGY=pool`) to cap OpenAI cost.
- Account deletion with Google token revocation.

## 2. Setup

**Prerequisites:** Node.js 24 (LTS) and Postgres 18. On macOS: `brew install postgresql@18 && brew services start postgresql@18`.

```bash
# 1. Databases (one for the app, one for tests)
createdb movie_memory
createdb movie_memory_test

# 2. Install (also generates the Prisma client and enables the pre-commit hook)
npm install

# 3. Configure: copy the template and fill it in (see section 3)
cp .env.example .env

# 4. Create the schema
npm run db:migrate

# 5. Run
npm run dev            # http://localhost:3000
```

**Google OAuth:**
1. In Google Cloud Console, go to **APIs & Services → Credentials → Create credentials → OAuth client ID** and pick type **Web application**.
2. Add the authorized redirect URI `http://localhost:3000/api/auth/callback/google`.
3. Put the client ID and secret in `.env`.

**Tests:** they use the separate test database and never call Google or OpenAI (a fake fact generator is injected).

```bash
npm run db:test:prepare   # apply migrations to the test database
npm test                  # vitest run
```

Other scripts: `npm run typecheck`, `npm run lint`, `npm run format`, `npm run build`. A git pre-commit hook runs migrations on the test DB, typecheck, lint and the full test suite, and blocks the commit if anything fails.

## 3. Environment variables

All of them are validated at startup with Zod (`src/lib/server/env.ts`); the app refuses to start with a clear list of what's missing. None use the `NEXT_PUBLIC_` prefix, so nothing here is sent to the browser.

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | yes | Postgres connection, e.g. `postgresql://<user>@localhost:5432/movie_memory`. Hosted Postgres usually needs SSL. |
| `TEST_DATABASE_URL` | for tests | The test database. Tests refuse to run without it and never touch `DATABASE_URL`. |
| `BETTER_AUTH_SECRET` | yes | Signs session cookies. At least 32 characters: `openssl rand -base64 32`. |
| `BETTER_AUTH_URL` | yes | The app's public base URL (`http://localhost:3000` locally). |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | yes | Google OAuth credentials. |
| `OPENAI_API_KEY` | yes | Server-only OpenAI key. |
| `OPENAI_MODEL` | no | Defaults to `gpt-6-luna`, the cheapest non-deprecated model at build time (about $0.0001 per fact). |
| `FACT_STRATEGY` | no | `generate` (default; Variant A as written) or `pool` (shared facts, capped OpenAI cost). |
| `FACT_POOL_SIZE` | no | The pool cap per movie (default 10). |

## 4. Database migrations

Migrations live in `prisma/migrations/` and are applied with Prisma Migrate:

| Command | When |
|---|---|
| `npm run db:migrate` (`prisma migrate dev`) | Local development: applies migrations (and creates new ones after schema changes). |
| `npm run db:test:prepare` | Applies the same migrations to the test database. |
| `npx prisma migrate deploy` | Production and CI: applies pending migrations only, never generates or resets. |

The history, in order: users → movies and facts → database-clock timestamps → fact history and leases → auth sessions/accounts → optional release year. Every schema change got a new migration; applied migrations were never edited.

## 5. Architecture overview

### Request flow

```
Browser ──► proxy.ts  (optimistic only: no session cookie → redirect to "/")
   │
   ├─► Pages (server components)          ──► page guards ─┐
   └─► Route handlers (/api/...)          ──► requireUser()┤  authoritative: session
          auth → validate (Zod) → service → map errors     │  checked in the DB
                                                           ▼
                              src/lib/server/  (services, server-only)
                              ├─ movies/   favorites, search
                              ├─ facts/    fact service, lease, queries
                              ├─ openai/   FactGenerator, prompt, output validation
                              └─ account/  profile, deletion, Google revocation
                                      │                    │
                                   Prisma ──► Postgres   OpenAI API
```

- **Thin routes, logic in services.** Route handlers do four things only: get the user from `requireUser()`, validate input, call a service, and turn errors into the shared JSON shape `{ "error": { "code", "message" } }`. Services take the `userId` and their dependencies (e.g. the fact generator) as parameters, so tests can inject fakes.
- **Two layers of auth.** `proxy.ts` (Next 16's middleware) only checks that a session cookie exists, for fast redirects; it's never trusted. Every page and endpoint calls `requireUser()`, which verifies the session against the database. Sessions are database rows, so deleting one logs that device out immediately.
- **Server-only boundaries.** Prisma, OpenAI and secrets live under `src/lib/server/` (every file imports `server-only`, so importing them from client code fails the build). Shared types and Zod schemas live in `src/lib/shared/`.

### Data model

| Table | Holds | Notes |
|---|---|---|
| `user`, `session`, `account`, `verification` | Better Auth's tables (CLI-generated) | Database sessions; the Google tokens live on `account`. |
| `Movie` | One row per real movie: normalized title + optional year | Shared across users. Status: `PENDING` → `VERIFIED` / `NOT_RECOGNIZED`. |
| `UserFavoriteMovie` | User ↔ movie link | `UNIQUE(userId)` for one favorite per user; dropping it allows many. |
| `MovieFact` | Fact text + the model that wrote it | Belongs to a movie, contains no personal data, so it's shareable. |
| `FactDelivery` | Which user was shown which fact, and when | The per-user history that drives the 60 s cache. |
| `FactGenerationLease` | "Generation in progress" for (user, movie) | Expires after 20 s, so a crashed request can't block anyone. |

Why it's shaped this way:
- **Fact content is shared but fact *history* is per user.** Facts can be reused (fallback, pool), and account deletion removes the history while keeping the anonymous facts.
- **`FactDelivery.movieId` is copied from `MovieFact`** so the cache check is a single index lookup. A **composite foreign key** `(movieFactId, movieId) → MovieFact(id, movieId)` makes the database guarantee the copy always matches.
- **All timestamps are `timestamptz` and filled in by Postgres.** Tests caught Prisma's `@default(now())` sending the app server's time instead.
- **Titles are normalized** (Unicode NFKD, accents stripped, lowercase, punctuation → spaces), so "Dune: Part Two" and "dune part two" are the same movie. A no-year movie is unique per title via a partial unique index (Postgres treats NULLs as distinct in normal unique indexes).

### Fact request: `GET /api/movies/:movieId/fact`

1. **Authorize.** The movie must be this user's favorite, otherwise **404** (never 403, so other users' data isn't revealed). A movie already marked `NOT_RECOGNIZED` returns 422 with no API call.
2. **Cache.** If the user's latest delivery is under 60 s old (compared in SQL against `now()`), return it as `cache`.
3. **Lease.** Claim the right to generate with one atomic statement:
   ```sql
   INSERT INTO "FactGenerationLease" (...) VALUES (..., now() + interval '20 seconds')
   ON CONFLICT ("userId", "movieId") DO UPDATE SET ...
     WHERE "FactGenerationLease"."lockedUntil" < now()   -- take over only an expired lease
   RETURNING "holderId";
   ```
   A returned row means we won. No row means another request is generating.
4. **Lost the lease.** Poll the cache every 250 ms for up to 2 s (the winner usually finishes), then fall back.
5. **Won the lease.** Re-check the cache (another request may have just finished), then call OpenAI **outside any transaction**, with a 12 s deadline covering the call, one retry and moderation. Save the fact and the delivery in one transaction. The lease is always released in a `finally`.
6. **Failure fallback.** On a timeout, API error, invalid output or moderation flag, return the user's most recent fact as `stale: true`, else the newest fact any user got for this (verified) movie, else **503** "We couldn't get a fact right now. Please try again in a moment."

### OpenAI integration (safety)

- **Only the title and year are sent**, never personal data.
- **Structured output** (a strict JSON schema `{ found, fact }`), **re-validated with Zod**: empty or over-500-character facts are rejected.
- **Prompt-injection defenses:** the rules sit in the system message, the title sits in delimited JSON with `<` `>` escaped (so it can't fake the closing delimiter), there are no tools, and responses aren't stored on OpenAI's side.
- **Moderation** runs on every generated fact before it's stored.
- **Retry** at most once, only for connection errors, 429 and 5xx; the SDK's own retries are disabled so ours is the only one.
- **Safe rendering:** facts are rendered as plain React text, never as HTML.

## 6. Variant choice: A, and why

I chose **Variant A** because the interesting problems in this app are on the backend, where a wrong answer is invisible until it's expensive. The cache window, the race when a user opens three tabs, and what to show when OpenAI is down are all places where code can look right and still double-charge the API or show stale data. Variant A's emphasis (data modeling, concurrency reasoning, safe OpenAI integration) also matches how I like to work: make the database the source of truth, then prove the edge cases with tests rather than by eye.

## 7. Key tradeoffs

| Decision | Why | Cost |
|---|---|---|
| **A database lease** for burst protection (over an in-memory lock, a transaction lock, or a unique constraint per 60 s bucket) | Works across multiple servers, prevents duplicate *API calls* (not just duplicate rows), holds no DB connection during the slow OpenAI call, and frees itself if a server crashes | More moving parts; the requests that lose need a policy (poll, then fall back) |
| **The database clock** for every freshness comparison | One clock shared by all servers, no clock skew | Tests can't use fake timers; they insert backdated rows instead |
| **Shared facts, per-user history** | Enables the fallback and the pool, and makes deletion clean | More tables than a single `Fact` table |
| **`generate` as the default strategy**, `pool` opt-in | Variant A literally says "generate a new fact" | The pool would be cheaper; I'd confirm with the product owner before making it the default |
| **No OpenAI call at onboarding**; recognition is learned from the first fact request | Onboarding stays fast and works when OpenAI is down | A made-up title is saved, then shown as "not recognized" (the user can edit it) |
| **Optional release year** | Disambiguates remakes without forcing users to know the year | "Dune" and "Dune (2021)" can exist as separate movies; the no-year uniqueness relies on a Prisma preview feature (partial indexes, verified drift-free) |
| **Better Auth** over Auth.js | Actively maintained (Auth.js is in maintenance mode, v5 still beta), self-hosted, users stay in our Postgres | A younger library with fewer community answers |
| **Database sessions** over JWTs | Revocable: logout and account deletion take effect immediately | A DB lookup per request |
| **Hard delete** with typed confirmation, best-effort Google revocation | Real erasure; no soft-delete filter on every query | No undo. Revocation can fail if the access token has expired (we deliberately don't store refresh tokens) |
| **Tests against real Postgres**, run serially | Catches real SQL behavior: constraints, `ON CONFLICT`, races, the DB clock | Slower than mocks; test files can't run in parallel |
| **Not deployed** | The brief asks for a repo; the app is deployable on any Node host (section 9) | Reviewers run it locally |

How the tests prove the hard parts: timing-dependent races (two tabs editing at once, a status update racing another user's) are made **deterministic** by holding the contested rows in an uncommitted transaction until Postgres reports every contender blocked. I also **mutation-checked** the core rules (deliberately breaking the code and confirming the right test fails), so passing tests actually mean something.

## 8. What I'd improve with 2 more hours

These are the next steps I'd take, in rough priority:

- **Movies:**
  - **Verify titles at onboarding** against a real movie database. IMDb has no free official API, so TMDB or OMDb (checking their current terms and limits). This also adds external ids for disambiguation and lets onboarding reject unknown titles instead of saving them as `PENDING`.
  - **Moderate user-entered titles**, since titles appear in other users' autocomplete.
  - **Fuzzy autocomplete** with Postgres `pg_trgm` (widely supported by hosted Postgres).
  - **Multiple favorites:** drop the temporary `UNIQUE(userId)` constraint. The schema and `GET /api/me` (which already returns a list) are ready for it.
- **Accounts:** **soft delete with a grace period and a purge job**, the GDPR-aware production pattern, instead of an immediate hard delete.
- **Hardening:**
  - **Rate limiting** on the search and fact endpoints.
  - **A circuit breaker for OpenAI outages**, so every refresh doesn't wait out the full 12 s deadline while OpenAI is down.
- **Fact strategy:** possibly make `pool` the default, after confirming with the product owner.
- **Deployment:** a live deployment (Vercel + Neon, or Heroku), if the hiring team wants one.

## 9. Deploying (guide only)

The app isn't deployed for this submission, but it runs on any Node host: there's no platform-specific code, all config comes from env vars, and migrations run via `prisma migrate deploy`.

**Checklist**
1. Provision Postgres with SSL.
2. Set every variable from section 3 on the host. `BETTER_AUTH_URL` must be the production URL.
3. Add `https://<your-domain>/api/auth/callback/google` as an authorized redirect URI in Google Cloud Console.
4. Run `npx prisma migrate deploy` once per deploy, before new code serves traffic.
5. Build with `npm run build` and start with `npm start` (it respects `$PORT`).

**Vercel + Neon:**
- It's serverless, so many instances run at once; the database lease already handles that.
- Use Neon's pooled connection string for the app and the direct one for migrations, and run migrations in the build step.
- Configure OAuth for the production domain only (preview URLs change).
- Make sure the function time limit exceeds the 12 s generation deadline.

**Heroku:**
- A `Procfile` with `web: npm start` and `release: npx prisma migrate deploy`.
- Heroku Postgres (SSL), with config vars for the env.

## 10. AI usage

I used AI throughout, and I can explain every line that was submitted.

- **Design:** I used Claude to brainstorm and stress-test the architecture (auth library, schema, concurrency strategy, failure handling), then wrote `SPEC.md` (what to build) and `CLAUDE.md` (how to work) to guide Claude Code.
- **Implementation with Claude Code, under rules I set:**
  - One step at a time, with my approval before each step and each commit.
  - Test-driven development from step 2 onward: each test was seen failing before the code existed. Tests for the earlier setup were written afterwards and mutation-checked.
  - A pre-commit hook that blocks any commit with a failing check.
- **Verifying against current docs, not memory:**
  - The tool versions it checked caught TypeScript 7 being incompatible with typescript-eslint, `prisma@latest` being a release candidate, and the cheapest OpenAI model (`gpt-5-nano`) being scheduled for shutdown within weeks. I chose `gpt-6-luna` instead.
- **Tests that caught real bugs:**
  - Prisma's `@default(now())` sends the app server's time.
  - Prisma doesn't escape SQL `LIKE` wildcards.
  - A concurrency test only raced when run alone; it was replaced with a deterministic race harness.
- **Mutation testing:** I had the AI break the code on purpose to prove each core test can fail (tests written after the code always pass at first).
- **Review against the brief:** when I compared the finished app to this take-home's PDF, the AI mapped every requirement and found one regression (a redesign had broken the first-time onboarding redirect), which we fixed.
- **Where I overrode or redirected it:** the UI flow (editing, an optional year), the model choice, commit granularity, and keeping `generate` (not `pool`) as the default to match the brief.
